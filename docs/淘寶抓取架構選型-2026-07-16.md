# 淘寶抓取（F3）架構選型備忘

> 作者：Fable 總指揮（2026-07-16）。老闆已表態此功能優先度提前（回饋 48）。
> 本備忘給老闆選路線用；選定後才立包，估算屬粗估。

## 問題本質
淘寶反爬是業界最兇等級：商品頁要登入、有滑塊驗證、指紋偵測。
「寫個爬蟲」不難，難的是**長期穩定跑而不被封**——這是基礎設施選擇，不是程式技巧。

## 四條路線

### 路線 D｜瀏覽器擷取小工具（Fable 推薦 ⭐）
你平常本來就會在自己的 Chrome 開淘寶商品頁挑貨。做一個小擷取器
（瀏覽器擴充或書籤按鈕）：**你人在商品頁上按一下**，它把頁面上的
標題/價格/規格/圖片網址整包送進上架工具，自動填表。
- 成功率：≈100%（用你真實登入的瀏覽器看頁面，淘寶眼中就是你本人在逛，無反爬問題）
- 成本：零月費、零維護；工程量小（一個擴充＋一支接收 API）
- 代價：每件要按一下（但你本來就會開頁面挑貨，多的只是一鍵）
- 風險：極低（不自動化瀏覽行為，不碰帳號安全）

### 路線 A｜強化現有輕量抓取（B3-fetch 加強版）
加強 header 偽裝、行動版頁面、快取。不用瀏覽器。
- 成功率：低（淘寶多數頁面直接擋），天花板明顯
- 定位：只當 D 的後備補充，不值得單獨立包

### 路線 B｜自架無頭瀏覽器服務（傳統 F3 想像）
VPS 常駐 Playwright＋維護你的淘寶登入 cookie，全自動抓。
- 成功率：中，但**驗證碼/封鎖是持久戰**，cookie 過期要人工救
- 成本：VPS 月費（約 US$5–20）＋持續維護心智＋帳號被風控的風險
- 適合：未來要「批量自動掃貨」（F 選品爬蟲全自動化）時再上

### 路線 C｜第三方抓取 API（按次付費）
用商用服務代抓（別人養瀏覽器農場）。
- 成功率：高、零維護；按件計費（每千次約 US$1–10 級距，依服務）
- 風險：資料完整度看服務商；長期成本隨量上升
- 適合：D 上線後若量大到按鍵也嫌煩，或 F 階段自動選品需要

## 建議決策
1. **現在：走 D**。單人店主、每天幾件到幾十件的量，一鍵擷取是成功率、成本、
   工期三優的解，而且完全繞開反爬軍備競賽。
2. F 階段（自動選品/週報）再評估 B 或 C——那時是「機器自己去逛」的需求，才值得養基建。
3. D 的立包時機：包一＋流程重構 R1/R2 之後（依老闆「優先度提前」指示，排在 R3/R4 之前可討論）。

## D 路線的粗規格（立包時細化）
- 擷取端：Chrome 擴充（Manifest V3）或書籤小工具；抓 DOM 的標題/價格/SKU 表/圖片 URL/參數表
- 接收端：`POST /api/import/product-page`（登入保護），落草稿＋自動填表＋去重檢查（沿用 A12）
- 圖片：擷取原圖 URL 由伺服器代抓入 Storage（單次、非爬蟲行為）
- 誠實原則：擷取不到的欄位留空，不猜
