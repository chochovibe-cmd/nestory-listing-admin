## 0. 白話：這包做什麼
1. **同步不再蓋掉 Shopify 後台的「售完」**：工具裡庫存是「無上限」的款，同步時完全不碰 Shopify 的庫存設定（追蹤／賣完不接單／數量）。工具裡設了「N 件（賣完即止）」的款照舊由工具管。
2. **來源售完 → Shopify 售完（按鈕，不自動）**：已上架商品的卡片上，若有款式來源售完，出現「來源售完 N 款」按鈕 → 開視窗先讀 Shopify 現況、列出要改的款 → 按「確認套用」才寫 Shopify。來源補貨了，同一個視窗可以「恢復可賣」（只恢復工具自己設過售完、而且 Shopify 上沒被人改過的款）。
3. **第一次發布／同步新增的款**：來源售完的款（老闆從「已排除」加回來的）直接以「售完」建立（DENY、數量 0）。
4. **款式表小提示**：來源剩 1–5 件顯示「來源剩 N」；工具已在 Shopify 設售完的款顯示「Shopify 已設售完」。
5. **修 CAPTURE-FIX 副作用**：重抓已上架商品只更新來源庫存，卻讓卡片變「Shopify 有未同步修改」→ migration 讓只改 `source_options` 的更新不再標髒。

不做：低庫存通知／排程自動同步、「只建真實組合」（匯入已只建抓到的組合）、Shopify 權限檢查畫面、刪除款式。

## 5. 伺服器（`src/lib/shopify/sourceStockSync.ts`）
### 5.1 GraphQL（匯出常數，ST13）
```graphql
query ProductSourceStock($id: ID!) {
  product(id: $id) {
    id
    variants(first: 100) {
      nodes {
        id inventoryPolicy
        inventoryItem {
          id tracked
          inventoryLevels(first: 20) {
            nodes { location { id name } quantities(names: ["available"]) { name quantity } }
          }
        }
      }
    }
  }
}
```
```graphql
mutation SourceStockVariants($productId: ID!, $variants: [ProductVariantsBulkInput!]!) {
  productVariantsBulkUpdate(productId: $productId, variants: $variants) {
    productVariants { id inventoryPolicy inventoryItem { id tracked } }
    userErrors { field message }
  }
}
```
不准用其他庫存 mutation，不准送價格（ST13）。

### 5.2 `planSourceStockSync({ variants, remote })`（ST04）
`remote` 是已換算到設定出貨地點的扁平陣列 `{ id, inventoryPolicy, tracked, available: number | null }`（`available` = 該 location 的 available，沒有該 location 的庫存紀錄 = null）。只用 `shopify_variant_id` 對應，不用名稱猜。
`remoteSoldOut = policy === "DENY" && tracked && available !== null && available <= 0`。

| 來源 stock | 條件 | 結果 |
|---|---|---|
| 任何 | 沒有 `shopify_variant_id` 或 remote 找不到 | skipped `not_on_shopify`（只有來源 sold_out 或 mark 為 sold_out 時才列出，其他不列） |
| sold_out | remoteSoldOut | skipped `already_sold_out` |
| sold_out | available === null | skipped `no_level` |
| sold_out | 其他 | soldOut，`prev = { policy, tracked, available }` |
| in_stock | mark=sold_out 且 remoteSoldOut | restore，`to = mark.prev` |
| in_stock | mark=sold_out 但不是 remoteSoldOut | skipped `manual_change`（有人在 Shopify 手動改過，不碰） |
| in_stock 無 mark／unknown／無 stock | — | 不列 |

每筆 action：`{ variantId, shopifyVariantId, label, ... }`，`label` = option1–3 非空值用「／」連接。回傳 `{ soldOut, restore, skipped }`。

### 5.3 `runSourceStockSync({ serviceSupabase, draftId, mode, expectedVariantIds?, now?, deps? })`
順序固定（ST05–ST12）：
1. `deps.callGraphQL` 沒給且 `SHOPIFY_PUBLISH_MOCK !== "false"` → `409 mock_mode`「安全模式：不會寫入 Shopify」。
2. 讀 `product_drafts`（`id, shopify_product_id, shopify_sync_status`）。沒有真實 product id（null 或 `mock-product-id`）→ `409 not_published`「這件還沒上架到 Shopify」；狀態 `remote_deleted` → `409 remote_deleted`「Shopify 上找不到這件商品」。
3. `locationId = "locationId" in deps ? deps.locationId : process.env.SHOPIFY_LOCATION_ID?.trim() || null`；沒有 → `409 location_required`「缺少 SHOPIFY_LOCATION_ID，請先在 Vercel 設定出貨地點；Shopify 沒有被改動」。
4. 讀 `product_variants`（`id, shopify_variant_id, option1_value, option2_value, option3_value, source_options`，`.eq("draft_id", draftId)`）。
5. `ProductSourceStock` 讀 Shopify。`!response.ok` 或有 `errors` → `502 inventory_read_failed`「讀不到 Shopify 庫存：Shopify App 需要 read_inventory 權限；Shopify 沒有被改動」。`product === null` → `409 remote_deleted`。
6. plan。`mode === "preview"` → `{ ok: true, mode, plan }`。
7. apply：`expectedVariantIds`（排序後）必須等於 soldOut＋restore 的 variantId（排序後），否則 `409 plan_changed`「Shopify 庫存剛剛有變，請按「重新檢查」」（沒傳也算不等，ST08）。兩邊都空 → `{ ok:true, mode, plan, applied:{soldOut:0,restore:0,failed:[]} }`，不呼叫 mutation。
8. 一次 `SourceStockVariants`，每款輸入**完全照下面**（ST06／ST07；欄位不可多）：
   - soldOut：`{ id, inventoryPolicy: "DENY", inventoryItem: { tracked: true }, quantityAdjustments: [{ locationId, adjustment: -prev.available, changeFromQuantity: prev.available }] }`；`prev.available === 0` 時不帶 `quantityAdjustments`。
   - restore：`{ id, inventoryPolicy: to.policy, inventoryItem: { tracked: to.tracked } }`；若 `to.tracked && to.available > 0` 再加 `quantityAdjustments: [{ locationId, adjustment: to.available, changeFromQuantity: 0 }]`。
9. 不論 mutation 成敗，**再讀一次** `ProductSourceStock`。讀失敗 → `502 inventory_read_failed`「Shopify 可能已部分改動，請按「重新檢查」確認」，不寫 DB（ST11）。
10. 逐款核對：soldOut 成功＝DENY＋tracked＋available===0；restore 成功＝policy、tracked 等於 `to`，且 `to.tracked` 時 available===`to.available`。成功的款才寫 DB：只更新 `source_options`（保留其他鍵）＝`{ ...舊, shopify_stock: { applied, at: now, prev } }`（restore 的 prev 為 null）。失敗的款進 `failed: [{ variantId, label, message }]`，message＝第一個 userError 的 message，沒有就「Shopify 沒有改成功」（ST10）。
11. 回 `{ ok: true, mode: "apply", plan, applied: { soldOut, restore, failed } }`。

錯誤回傳型別：`{ ok: false, status, code, error }`。

### 5.4 API `POST /api/drafts/[id]/shopify-stock`（ST16）
照 `shopify-sync/route.ts` 寫法：`runtime = "nodejs"`、`maxDuration = 60`、登入＋`canPublish(role)`（403「需要審核者權限」）。body：`{ mode: "preview" | "apply", expectedVariantIds?: string[] }` → `runSourceStockSync({ serviceSupabase: createServiceSupabaseClient(), draftId: id, mode: body.mode === "apply" ? "apply" : "preview", expectedVariantIds: Array.isArray(body.expectedVariantIds) ? body.expectedVariantIds.filter(s => typeof s === "string") : undefined })`。錯誤回 `{ error, code }` 和對應 status。不收、不轉送任何 Shopify ID。
