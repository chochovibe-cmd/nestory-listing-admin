# 部署平台定案：Vercel

整理日期：2026-07-04

## 結論

上架工具（這個 repo）**定案用 Vercel 部署**，不用 Cloudflare。

## 為什麼不是延續舊的 Cloudflare 方向

`分支/` 資料夾那個舊原型（單一 HTML + Cloudflare Worker）是完全不同的架構。現在這個上架工具是 Next.js 全端專案，本來就是 Vercel 原生支援的寫法，`next build` 直接過、零額外設定。

## 三個關鍵理由

1. **圖片裁切/補白這件事，Vercel 免費內建，Cloudflare 要多花錢。**
   規劃裡要做的「主圖裁成 1:1」「詳情圖統一寬度」這種基礎圖片處理，業界標準工具是 `sharp`，它需要完整 Node.js 環境才能跑。Vercel 有這個環境，裝了就能用，不用額外付費。Cloflare Workers 的環境跑不動 sharp，要做同樣的事得另外加購「Cloudflare Images」服務，或改叫 Cloudinary，等於多一筆錢、多一個要顧的帳號。

2. **OCR / 翻譯 / 去浮水印 / 重新生成圖，兩邊平台成本一樣，跟選哪個平台無關。**
   這幾項是要「讀懂圖片內容」的工作，本來就要另外呼叫 AI 服務，不管在 Vercel 還是 Cloudflare 上呼叫都一樣，沒有平台上的差別。

3. **Cloudinary 就算不留存圖片，一樣會扣免費額度。**
   Cloudinary 免費版是照「這個月處理了幾次、傳輸了多少資料」算，不是照「存了多久」算。就算只是「經過處理一下、馬上丟去 Shopify、不留在 Cloudinary」，這個處理動作本身還是照樣扣額度。改用 Vercel + sharp 自己處理，這筆帳完全不用算，因為那是自己的運算資源，沒有第三方在計費。

## 最終圖片處理流程

淘寶原圖 → Vercel 上用 sharp 裁切/補白/縮放 → 需要的話另外呼叫 AI 做 OCR/翻譯/去字 → 處理完的最終圖直接上傳到 **Shopify 媒體庫**，用 Shopify 回傳的網址上架。**不再經過 Cloudinary，也不用 Supabase Storage 存圖。**

## 老闆工具「一次傳多張圖會失敗」的原因，順便查到了

這不是「額度用完」，是 Vercel 的伺服器功能對「單次請求能傳的資料量」有硬性上限（約 4.5MB）。傳一張圖通常沒超過，一次傳好幾張疊加起來容易超過，整批直接被拒絕。上傳偏慢則是「冷啟動」——伺服器功能太久沒人呼叫，下次呼叫要先重新開機，這零點幾秒的延遲會有感。

**解法**：上傳圖片改成「一張一張傳」或「前端直接傳去圖床，不繞經自己的伺服器」。這是流程設計問題，不是平台問題，這個上架工具的上傳功能會從一開始就避開這個坑。

## CSV 匯出不用擔心流量

CSV 是純文字檔（商品資料 + 圖片網址，不含圖片本身），再大的商品庫匯出也就幾 MB，跟圖片傳輸完全不是同個量級，不會對 Vercel 的流量額度造成壓力。

## 整體用量：Vercel 免費版夠不夠用

這是團隊內部用的後台工具，不是對外公開的高流量網站，Vercel 免費版（Hobby）的用量額度綽綽有餘。Cloudflare「免費版比較大方」的名聲，主要來自「完全不收流量費」跟「幾乎零延遲啟動」，這些優勢對公開高流量網站影響大，對這種內部小工具差異不明顯。

## 給未來其他工具的參考原則

以後如果要做採購工具、儀錶板、金流統計、CRM/ERP 訂單管理這類**不需要處理圖片像素**的工具，Cloudflare 是合理的預設選擇，不用每個工具都綁定 Vercel。真正該問的關鍵問題只有一個：

> 這個工具會不會動到圖片本身（裁切/合成/辨識文字）？
> 會 → 傾向 Vercel。不會 → Cloudflare 大概率更省錢、更快。

（附帶兩個小提醒，遇到再處理即可：PDF/Excel 報表如果用到「開瀏覽器印成 PDF」這種技術一樣跑不動 Cloudflare，選純程式邏輯的套件就好；資料庫如果延續現在這種用 Supabase JS 套件存取的方式，不會踩到 Cloudflare 連資料庫的常見地雷。）
