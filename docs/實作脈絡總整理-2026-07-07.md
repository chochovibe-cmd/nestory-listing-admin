## 六、資訊架構規劃（2026-07-07 補充：回答「版面要怎麼加功能」）

### 現況診斷

目前整個系統實際上只有兩個頁面：
- `/drafts/new`：工作檯（左表單＋右結果卡片流），生成、審核、發布全部在這一頁完成
- `/drafts`：商品佇列清單
- `/review` 已被刻意合併掉（redirect 到 /drafts/new），手機導覽也只剩兩個 tab

這個「一頁打天下」是單人操作流的刻意簡化，商品量少時很順。
但要加圖片審核、儀表板、選品等功能時，不能繼續往右欄卡片流裡塞。

### 重要的好消息（不用重構的部分）

資料庫的狀態欄位早就拆開了：`generation_status`、`image_status`、`publish_status`、`sale_status`
各自獨立（`src/types/domain.ts`）。當初「狀態要拆開、避免日後加圖片 pipeline 要重構」的建議
**已經實作**。所以兩段式生圖的後端地基是預留好的，缺的只是前台沒有顯示與操作它的地方。

### 解法：加一層導覽外殼（App Shell），現有頁面不用重做

| 頁面 | 狀態 | 說明 |
|---|---|---|
| 新增商品（工作檯） | 現有，不動 | 左表單右結果，維持現在的樣子 |
| 商品佇列 | 現有，不動 | /drafts 清單＋批次操作 |
| 圖片審核 | **新增**（做圖片 pipeline 時一起做） | 讀 `image_status = 待審核` 的商品，確認使用／拒絕重生 |
| 儀表板 | 未來 | 上架統計、GSC / Shopify 數據、選品方向參考 |
| 選品情報 | 未來 | 爬蟲候選商品清單 → 一鍵帶入新增商品表單 |
| 設定 | 現有（散在 header） | 可整併成獨立頁 |

手機底部導覽從 2 個 tab 擴為 3–4 個。桌面版加側邊欄或頂部導覽列。

### 各未來功能在架構上的位置（一句話版）

- **兩段式生圖**：第二段是背景工作，完成後商品出現在「圖片審核」頁等你確認，不佔工作檯
- **選品爬蟲（Puppeteer + Vision，跑 VPS）**：上游模組，產出「候選商品」，跟上架主流程分離；
  選定的候選商品一鍵帶入新增商品表單，之後流程照舊
- **儀表板（GSC / Shopify 數據）**：獨立唯讀頁，拉 API 顯示，跟主流程零耦合；
  等有真實上架數據後再做才有意義（GSC 需先完成網站驗證）

### 建議施工順序

1. 接真 Shopify 發布（P0，不動 UI）
2. **Vision 接入**（讓 AI 真的看到圖片＋規格圖 OCR，見第七節問題 1）——成本低、對文案品質影響大
3. 收掉 mockup 剩餘小修（B-1 / B-4 / B-5，可選）
4. **App Shell 導覽改版**——在加任何第三個頁面之前先做這個
5. 圖片審核頁＋生圖 pipeline（第二段）
6. 儀表板（有數據之後）
7. 選品爬蟲（最後，依賴 VPS / n8n）

## 七、現有工具問題清單（2026-07-07 實地檢查程式碼後）

### 大問題（方向性缺口）

1. **AI 從來沒有真的看過圖片**。文案生成只吃「標題＋備註」。System prompt 寫著要模型
   「從標題與圖片描述判斷 IP」，但 `image_description` 欄位**沒有任何程式會寫入**，永遠是空的。
   當初規劃的「Vision 辨識主圖/詳情圖（GPT-4o-mini，約 $0.0004/商品）」和「規格圖 OCR 簡轉繁」
   兩步都還沒接。這是目前實作與規劃方向最大的落差。
2. **上傳區的徽章是「預告」不是事實**：主圖寫「1:1 裁切」、詳情圖寫「800px」、規格圖寫「OCR」，
   但實際上傳只是把原檔存進 Supabase Storage，任何處理都沒做（`processed_file_url` 直接等於原圖）。
   同事看了會誤以為系統有處理。建議徽章文案先改成誠實版本，或盡快接上處理。
3. Web Search 開關有 UI 沒後端（已知，系統會誠實警告，不算騙人，但要記得它還沒通）。

### 小問題（技術細節，交給扣哥修）

4. **預設模型過舊**：Claude 預設 `claude-sonnet-4-20250514`（已有 sonnet-5）、OpenAI 預設 `gpt-4o`。
   可用環境變數 `ANTHROPIC_COPY_MODEL` / `OPENAI_COPY_MODEL` 覆蓋（符合 Provider 可替換原則），但預設值該更新。
5. **max_tokens 1500 有截斷風險**：選「詳細」文風時，輸出的 JSON（描述＋FAQ＋SEO＋賣點）可能超過
   1500 token，被切斷會導致 JSON 解析失敗、整次生成報錯。建議調高到 3000 以上。
6. **規格圖文字有欄位沒接線**：`spec_text` 欄位和 provider 的 `specText` 參數都存在，
   但 `/api/generate` 沒有把它傳進去——就算欄位有值也不會進文案。跟問題 1 一起修。

### 方向對齊評估（回答「有沒有照我要的方向走」）

有對齊的：LLM API 為主寫文案 ✓、扣哥不寫文案 ✓、Provider 可替換（env 切換）✓、
Tags/Collections 永遠走規則引擎不給 LLM 亂寫 ✓、二手商品欄位 ✓、狀態欄位拆分 ✓、CSV 備援 ✓。

一個「刻意偏離」（不是走偏）：原規劃是「規則引擎先產骨架 → LLM 潤稿」，實際改成
「LLM 一次直接寫完、規則引擎只管 tags 和標題骨架」——這是 2026-07-02 確認過的修正，
因為潤稿模式產出太死板。程式註解有記錄原因。

一個「真缺口」：Vision 整段沒接（問題 1），已排進施工順序第 2 步。

### 選品策略定案（商家追蹤法，取代「教 AI 選品」）

結論：**不需要教 AI 判斷「值不值得賣」**，用商家追蹤繞開這個難題：

1. 你人工篩選 10–20 個定位相近的淘寶商家（一次性，之後維護即可）
2. 排程（每天/每週）掃描這些商家的商品列表：Puppeteer 開頁截圖 → GPT-4o-mini Vision
   讀出商品標題與價格（跑在 Hostinger VPS，跟 n8n 同一台，無額外主機成本）
3. 簡單規則過濾（不用 AI）：是否已收錄、價格是否在販售區間、圖片數量是否足夠
4. 符合的推播通知你審核 → 你看一眼 → 一鍵帶入上架工具的新增商品表單

不需要 Computer Use（流程固定、頁面版型固定，便宜方案就夠，成本約為 Computer Use 的 1/20）。
「24 小時不鎖電腦的 agent」概念＝跑在 VPS / 雲端的常駐程式，正是因為自架（Hostinger）才做得到；
這也是選品爬蟲排在 n8n 自架之後的原因。
