## Why this was needed

Vercel preview checks on recent stabilization commits reported failure with target `build-rate-limit / upgradeToPro`. That is an account/build-quota condition and did not provide a trustworthy code compile signal.

GitHub Actions was added as an independent gate so code correctness is not inferred from Vercel preview availability.

## Canonical CI pipeline

`.github/workflows/ci.yml` runs on push and pull_request:

1. `pnpm install --frozen-lockfile`
2. `pnpm run verify:all`
3. `pnpm run typecheck`
4. `pnpm run build`

Environment safety:
- no production secrets are injected
- CI-only placeholder Supabase values are used for compile-time configuration
- `SHOPIFY_PUBLISH_MOCK=true`
- workflow token permission is `contents: read`

## First-run findings

The CI gate immediately exposed pre-existing verifier drift. These were not application runtime regressions; they were checks whose assumptions no longer matched the repository.

### 1. `verify-static` contradicted P1-3 browser-storage policy

Old behavior:
- blanket-banned every `localStorage` occurrence except a filename allowlist
- rejected raw text labels such as `OPENAI_API_KEY`, even if the UI merely displayed the server environment variable name

This contradicted the newer P1-3 policy where non-sensitive browser state is allowed and credential-like storage writes are blocked.

Fix:
- added shared `client-secret-reference-policy.mjs`
- added `verify-client-secret-reference-policy.mjs`
- browser storage checks use the existing sensitive-write policy
- raw environment-variable names in explanatory UI text are allowed; actual client `process.env.<secret>` access remains forbidden

### 2. Client/server scope was path-based and too broad

A first verifier revision classified most `src/lib/**` as potentially client-side and therefore falsely flagged legitimate server helpers:
- `src/lib/supabase/server.ts`
- `src/lib/shopify/adminToken.ts`
- `src/lib/notifications/make.ts`
- other server-only helpers

Fix:
- added `scripts/client-module-graph.mjs`
- client scope now starts at actual `"use client"` modules and follows local imports transitively
- server modules are not false positives merely because they live under `src/lib`
- if a client component ever imports a server secret-bearing helper, that helper becomes client-reachable and the verifier will fail

Validated client graph on green run: **135 client-reachable modules**.

### 3. `verify-requirements` was coupled to retired v0.1 filenames

Old verifier required historical filenames such as:
- `docs/deployment-checklist.md`
- `docs/api-contracts.md`
- `docs/codex-skill-rules.md`
- `docs/manual-qa-checklist.md`
- `docs/completion-audit.md`
- `docs/v0.1-team-handoff.md`

This made a historical documentation layout part of the executable product contract.

Fix:
- created `docs/RELEASE_READINESS.md` as the canonical deployment/API/QA/completion/handoff release gate
- modernized `verify-requirements.mjs` to verify **23 current contracts** against source, fixtures, canonical docs, AI handoff docs, and the production Supabase audit
- deterministic fixtures remain required
- removed dependency on a retired hard-coded Codex skill version as a current project requirement

### 4. `verify-contracts` / `verify-mock-flow` also read missing legacy docs

Old paths included:
- `docs/worker-contract.md`
- `docs/mock-flow.md`
- `docs/codex-skill-rules.md`
- `docs/api-contracts.md`

Fix:
- worker output contract now checks `src/app/api/worker/complete/route.ts` + `fixtures/worker-complete-sample.json`
- Shopify/Matrixify contracts remain source/fixture based
- human-readable API and release safety contract comes from `docs/RELEASE_READINESS.md`
- mock-flow verifier retains deterministic fixture checks while using `RELEASE_READINESS.md` for documented confirmation/smoke expectations
