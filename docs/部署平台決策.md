# Deployment Platform Decision: Vercel (not Cloudflare)

Recorded: 2026-07-04
Context: discussion between the shop owner and Claude, ahead of the first
deployment of the Nestory listing admin (`codex/nestory-v0.1-safety-skeleton`).
This file is written for a future Claude/Codex session to read for full
context -- it captures the reasoning, not just the conclusion, so a later
session can judge whether the reasoning still holds if circumstances change.

## Decision

Deploy the Nestory listing admin (this repo) to **Vercel**, not Cloudflare
Pages/Workers.

## Why this question came up

The user has an earlier, unrelated prototype under `分支/` (a single static
HTML file + a Cloudflare Worker backend proxy, deployed to Cloudflare Pages --
see `分支/Claude V6/codex-handoff-v6.md` and `分支/README-v5-lightweight.md`).
That prototype's stack is why the user's default assumption was "we were
going to use Cloudflare." The current repo is architecturally unrelated: it's
a Next.js App Router app with server Route Handlers (`/api/worker/claim`,
`/api/drafts/[id]/publish`, etc.) and Supabase SSR, which is the stack Vercel
supports natively (`next build` already passes with zero extra config in this
repo, verified 2026-07-04).

## Core technical reason: sharp needs a Node.js runtime

The product plan (`nestory_codex_context_plan.md`, section 7) calls for image
pre-processing before upload: crop/pad the main image to a clean 1:1 canvas,
normalize detail-image width, and OCR + translate text on spec-sheet images.

The crop/resize/pad step is normally done with `sharp`, which wraps a compiled
C++ image library (libvips) -- it needs a full Node.js runtime to load that
native binary. `pnpm-workspace.yaml` in this repo already special-cases sharp's
install script for this reason.

- **Vercel** serverless functions run full Node.js, so `sharp` just works.
- **Cloudflare Workers** run on V8 isolates (deliberately lightweight, no
  native-binary loading), so the exact same `sharp` code cannot execute there
  at all -- not slow, not degraded, simply unable to run.

This is not about OCR. OCR/translation/watermark-removal/image-regeneration
are AI/vision-API calls (outbound HTTP), which work identically on either
platform -- the runtime distinction only affects the crop/resize/pad step,
because that's the only piece that needs a locally-executing native library
rather than an external API call.

## If Cloudflare were chosen anyway

Cropping/resizing would need to move to one of:

- **Cloudflare Images / Image Resizing** -- a separate paid add-on product
  (not bundled into the generous Workers free tier), does comparable
  geometric operations (resize/crop/pad-with-background) to sharp, but is
  metered and billed independently. Confirm current pricing before relying on
  this, since pricing pages change.
- **Cloudinary** -- see next section for why this is worse than doing it
  in-house on Vercel, even used purely as a pass-through step.
- A separate Node.js service just for image processing -- adds a second
  deployment target and cross-service calls, more moving parts than the
  problem justifies for v0.1.

Neither of these routes needs "AI" for the basic crop/resize step -- that
would be over-engineering. AI is reserved for the tasks that actually require
understanding image content (OCR, translation, watermark removal,
regeneration), and those cost the same on either platform.

## Why Cloudinary was dropped from the pipeline entirely

The user's `分支` prototype originally uploaded to Cloudinary and stored the
returned URL. A later iteration moved to Supabase Storage, then ran into
Supabase Storage's own capacity constraints, landing on "use an external tool
purely to transform, final image ends up in Shopify's media library."

Clarified during this discussion: Cloudinary's free tier is metered by
**transformations performed + bandwidth transferred that month**, not by how
long an image is stored. So using Cloudinary purely as a transient
crop-then-discard step still consumes the same monthly credits as if the
image were kept there permanently -- "don't keep the image" does not avoid
the quota. High enough listing volume (multiple images per product, multiple
sizes per image, daily uploads) will eventually hit the free-tier ceiling.

Decision: skip Cloudinary. Do the crop/resize/pad step with `sharp` running
inside a Vercel serverless function -- this is the team's own compute, not a
third-party metered service, so there is no monthly credit to track. Final
processed images upload directly to Shopify's media library via the Admin
API, and the returned Shopify CDN URL is what gets used on the listing. No
Supabase Storage or Cloudinary needed as an intermediate image store.

## Diagnosed bug in the user's other Vercel-deployed tool ("老闆工具")

Symptom reported: uploading several images in one batch usually fails;
uploading one image at a time usually succeeds; uploads feel slow generally.

Diagnosis given (architecture-level, not Vercel-specific quota exhaustion):

- Vercel serverless functions running the Node.js runtime (the runtime
  `sharp` needs) have a **hard per-request body size limit** (historically
  ~4.5MB). This is a per-request ceiling that applies from the very first
  request -- it is unrelated to monthly usage/quota. Multi-file multipart
  uploads easily exceed this when several images are combined into one
  request; a single image upload usually stays under it, matching the
  reported symptom exactly.
- General slowness is most likely **cold starts**: Node.js serverless
  functions spin up a fresh container after idling, adding user-visible
  latency before the first response. Cloudflare Workers (V8 isolates) have
  near-zero cold start by design, which is a genuine architectural advantage
  Cloudflare has here.

Fix is architectural and applies regardless of hosting platform:

- Upload images one at a time (sequential or parallel individual requests)
  instead of bundling several files into a single request body, and/or
- Upload directly from the client to storage (Shopify media / Supabase
  Storage signed upload) so large binary payloads never pass through the
  app's own serverless function body at all.

This should be designed correctly from day one in the Nestory upload flow
to avoid repeating the same bug.

## CSV export bandwidth (Matrixify fallback) is a non-issue

Clarified: CSV exports are plain text (product data + image *URLs*, not
embedded binary image data). Even a full-catalog export is realistically
KBs to a few MB. This is a different order of magnitude from image binary
transfer and does not meaningfully contribute to hitting Vercel's bandwidth
allowance, however large or frequent the exports are for this project's
scale.

## Overall usage-quota comparison (not per-request limits)

Two different kinds of "limits" were distinguished:

1. **Monthly usage quota** (how much total activity before cost/blocking) --
   for a small internal admin tool used by a handful of team members doing at
   most a few dozen operations a day, Vercel's free (Hobby) tier is expected
   to be comfortably sufficient. This is not a public, high-traffic
   consumer app.
2. **Per-request technical ceilings** (body size limits, execution duration,
   cold start latency) -- these are architecture constraints, not quota, and
   are what the boss's-tool bug above actually hit.

Cloudflare's reputation for a "generous free tier" mainly comes from: no
bandwidth/egress fees at all (an industry-known Cloudflare differentiator),
a higher raw request ceiling, and near-zero cold starts. These matter most
for public, high-traffic sites -- less so for a small internal tool that
will never generate that kind of traffic. So "Cloudflare rarely hits free
limits" is true, but the underlying reason (traffic-scale headroom) doesn't
translate into a meaningful advantage for this specific tool's actual usage
pattern.

## Guidance for future, unrelated tools (not this repo)

The user asked, separately, whether future tools with no image-pixel work
(procurement tool, dashboard, cash-flow/finance stats tool, CRM/ERP order
management) could default to Cloudflare instead.

Answer: generally yes. The deciding question for any future tool is: **does
it manipulate image pixels (crop/composite/OCR-adjacent binary processing)?**
If no, Cloudflare Workers/Pages has no structural disadvantage for typical
CRUD/dashboard/reporting workloads, and its no-bandwidth-fee, fast-cold-start
properties are a genuine plus.

Two residual watch-items to check per-tool, not blanket blockers:

- **PDF/Excel export**: if a tool wants "render HTML to PDF" via a full
  browser engine (e.g., Puppeteer), that also can't run on Workers, same
  underlying reason as sharp. Pure-JS export libraries (no native binary,
  no headless browser) work fine on Workers -- pick the library
  accordingly when that feature is actually built.
- **Direct Postgres driver connections**: raw TCP Postgres clients have
  historically been awkward on Workers. This project (and presumably future
  ones, if they keep the same pattern) uses `@supabase/supabase-js`, which
  talks to Supabase over HTTP/PostgREST rather than a raw TCP driver, so this
  concern does not apply as long as that access pattern continues.

Different tools are free to land on different platforms based on their own
needs -- there's no requirement to standardize on one platform across all of
the user's tools.
