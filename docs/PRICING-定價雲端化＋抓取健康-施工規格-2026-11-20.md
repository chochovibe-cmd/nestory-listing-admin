## 2. PRICING-RULES（定價規則，寫清楚＝跟程式一致；**算法不改**）
`src/lib/pricing.ts` 的 `calculatePrice` 算法一行都不准改。規則就是現在的程式：
1. 成本（台幣）＝ 人民幣成本 × 匯率 × 成本係數，無條件進位（成本係數＝運費手續費緩衝）。
2. 售價 ＝ 成本（台幣）× 利潤係數，至少「最低售價」，再尾數美化。
3. 定價（劃線價）＝ 成本（台幣）× 定價係數，至少等於售價，再尾數美化；美化後若不高於售價，跳下一階美化價。「單一售價」商品沒有定價。
4. 利潤 ＝ 售價 − 成本（台幣）。
5. Showmore 匯出時售價／定價另加 Showmore %，再尾數美化（成本不加）。
6. 手填售價、手填目標利潤照舊（不在本包範圍）。

本包要做的規則部分只有三件：
- **R1 數字範圍**（存雲端前檢查，前端與 API 用同一個函式）：

  | 欄位 | 名稱 | 範圍 |
  |---|---|---|
  | rate | 匯率 | 3–7 |
  | costMultiplier | 成本係數 | 1–2 |
  | marginMultiplier | 利潤係數 | 1–4 |
  | compareAtMultiplier | 定價係數 | 1–5 |
  | minPrice | 最低售價 | 0–3000 的整數 |
  | showmoreMarkupPercent | Showmore 加價% | 0–30 |

  錯誤訊息（一字不改）：`{名稱}要在 {min}–{max} 之間`；最低售價：`最低售價要是 0–3000 的整數`。不是數字也用同一句。
- **R2 公式說明改成跟程式一致**（兩處 UI 的 `.formula-preview`，見 §4.3）。
- **R3 低利潤提醒**：利潤係數 < 1.15 時，設定區顯示一行 `price-soft-warn`（見 §4.3）。只是提醒，不擋儲存、不改任何價格。
- **R4 設定版本快照**：`PricingSettings` 加選填欄位 `version?: string | null`（＝雲端那列的 `updated_at`）。不用改 `calculatePrice`：它本來就把 `settings` 整包寫進 `pricingFormula`，有 version 就會一起記下來。

### 3.2 新檔 `src/app/api/settings/pricing/route.ts`（只 export `GET`、`PUT`）
權限照 `src/app/api/settings/capture-token/route.ts` 的寫法：`createServerSupabaseClient` 取 user → 沒登入 401 `{ ok:false, error:"Unauthorized", message:"請先登入" }`；讀 `profiles.role`，`canOperate` 不過 → 403 `{ ok:false, error:"forbidden", message:"需要 operator、reviewer 或 admin 角色" }`；service role 缺 → 503 `{ ok:false, error:"server_misconfigured", message:"伺服器未設定 SUPABASE_SERVICE_ROLE_KEY" }`。

- `GET`：讀 `team_settings` where key=`pricing_settings`。
  - 沒有那列 → 200 `{ ok:true, settings:null, updatedAt:null }`
  - 有，且 `validatePricingSettings(value)` 通過 → 200 `{ ok:true, settings:{...settings, version: updated_at}, updatedAt: updated_at }`
  - 有但壞掉 → 500 `{ ok:false, error:"invalid_cloud_settings", message:"雲端定價設定格式不正確，請到設定頁重新儲存一次" }`
  - 資料庫錯誤 → 500 `{ ok:false, error:"db_error", message:"讀取雲端定價設定失敗" }`
- `PUT`：body `{ settings: Partial<PricingSettings> }`。
  - base＝雲端現有（通過檢查才用）否則 `defaultPricingSettings`；merged＝`{ ...base, ...pickEditablePricing(body.settings) }`。
  - `validatePricingSettings(merged)` 失敗 → 400 `{ ok:false, error:"invalid_settings", field, message }`。
  - upsert `{ key:"pricing_settings", value: 6 個欄位, updated_by: user.id }`（`onConflict: "key"`），再讀回 `updated_at`。
  - 成功 → 200，形狀同 GET。前端傳來的 `version`、其他欄位一律忽略。
  - 寫入錯誤 → 500 `{ ok:false, error:"db_error", message:"存到雲端失敗" }`。

### 3.3 改寫 `src/lib/pricingSettingsStore.ts`（保留 "use client"；**兩個舊函式名字與回傳型別不變**，讓其他檔案不用改）
狀態（模組內變數）：`cloudSettings: PricingSettings | null`、`status: PricingSyncStatus`、`loadStarted: boolean`、`pendingPatch`＋debounce timer。

```ts
export type PricingSyncState =
  | "local_only"   // 沒有 Supabase 環境（本機 mock 模式）：完全照舊用 localStorage
  | "loading" | "cloud" | "cloud_empty" | "load_error"
  | "saving" | "saved" | "save_error" | "invalid";
export type PricingSyncStatus = { state: PricingSyncState; message?: string | null; updatedAt?: string | null };
export const PRICING_SYNC_STATUS_EVENT = "nestory:pricing-sync-status";
export function getPricingSyncStatus(): PricingSyncStatus;
export function getStoredPricingSettings(): PricingSettings;           // 同步回傳，見下
export function setStoredPricingSettings(patch: Partial<PricingSettings>): void;
export function seedCloudPricingFromThisDevice(): Promise<{ ok: boolean; message?: string }>;
```
- `getStoredPricingSettings()`：SSR 回 `defaultPricingSettings`。前端：第一次被呼叫時（且 `hasSupabaseBrowserEnv()` 為真）啟動一次 `GET /api/settings/pricing`（只啟動一次，之後不再打）。回傳順序：`cloudSettings` → localStorage 快取 → 預設值。沒有 Supabase 環境＝`local_only`，行為跟現在一模一樣。
- 載入結果：
  - 有雲端設定 → `cloudSettings`＝它；寫回 localStorage 快取；狀態 `cloud`（帶 updatedAt）；**只有跟載入前回傳的值不同時**才發 `nestory:pricing-settings-changed`（detail＝新設定），避免工作台的「利潤驅動」一開頁就被關掉。
  - 雲端沒有（settings:null）→ 狀態 `cloud_empty`；繼續用這台的 localStorage（＝現況，不自動上傳）。
  - 失敗 → 狀態 `load_error`（message＝API 的 message 或「連線失敗」）；繼續用 localStorage 快取。
- `setStoredPricingSettings(patch)`：
  - `local_only`／`cloud_empty`：照現在寫 localStorage＋發事件（`cloud_empty` 時只影響這台，跟現在一樣）。
  - `loading`／`load_error`：不寫、不發事件（UI 那時輸入框是 disabled，這裡是保險）。
  - `cloud`／`saved`／`save_error`／`invalid`／`saving`：先 merge 出 next，`validatePricingSettings(next)` 失敗 → 狀態 `invalid`（message＝檢查訊息），**不改快取、不發設定事件**。通過 → 立刻更新 `cloudSettings`＋localStorage＋發設定事件（畫面立即重算），並把 patch 累積起來，**800ms debounce** 後 `PUT`；送出時狀態 `saving`。
  - PUT 成功 → `cloudSettings`＝回傳值，狀態 `saved`，2 秒後轉回 `cloud`（updatedAt 更新）。
  - PUT 失敗 → 把 `cloudSettings`、localStorage 改回最後一次成功的雲端值，發設定事件（輸入框跟著改回），狀態 `save_error`（message＝API message 或「連線失敗」）。
- `seedCloudPricingFromThisDevice()`：只在 `cloud_empty` 可用；把這台現在的 6 個值整包 PUT；成功 → 狀態 `cloud`；失敗回 `{ ok:false, message }`、狀態維持 `cloud_empty`。
- 每次狀態改變發 `PRICING_SYNC_STATUS_EVENT`（detail＝status）。
- localStorage 的 key 仍是 `nestory_pricing_settings`（舊裝置設定就在這裡，`cloud_empty` 時拿來顯示與上傳）。

### 4.1 新檔 `src/lib/import/captureHealth.ts`（純函式，前端可 import；不碰網路、資料庫）
```ts
export type CaptureHealthIssueCode =
  | "variant_cost_missing" | "variant_cost_unconfirmed"
  | "same_price_with_range" | "no_variants" | "no_detail_images";
export type CaptureHealthIssue = { code: CaptureHealthIssueCode; label: string };
export type CaptureHealthInput = {
  rawCapture: unknown;                    // product_drafts.raw_capture（或 {client_meta, server}）
  productCny: number | string | null | undefined;
  variants: Array<{ cny_price?: number | string | null; cost_is_inherited?: boolean | null }>;
  detailImageCount: number;               // 現在這筆草稿 image_type === "detail" 的張數
  shopifyProductId?: string | null;
};
export const CAPTURE_HEALTH_TITLE = "抓取可能不完整，建議重抓";
export function assessCaptureHealth(input: CaptureHealthInput): { incomplete: boolean; issues: CaptureHealthIssue[] };
export function captureHealthHowTo(issues: CaptureHealthIssue[]): string;
```
規則（依序，`usable(x)`＝有限數字且 > 0.01）：
0. **不檢查**（回 `{incomplete:false, issues:[]}`）：`rawCapture` 不是物件、或既沒有 `client_meta` 物件也沒有 `server` 物件（＝不是外掛抓的）；或 `shopifyProductId` 是非空字串且不是 `"mock-product-id"`（已上架：重抓只會更新庫存，不會改價）。**這個判斷在 captureHealth.ts 內自己寫（跟 `isRealShopifyProductId` 同邏輯），不准 import `src/lib/shopify/productLifecycle.ts`**——那支會帶進 Shopify Admin 伺服器程式，卡片是前端元件。
1. 有款式（`variants.length ≥ 1`）時：
   - `missing`＝自己的成本不可用、且商品成本也不可用的款數。> 0 → `variant_cost_missing`，label `款式價格有缺（{missing} 款沒有成本）`。
   - `isVariantPriceUnconfirmedCapture(rawCapture)` 為真時，`inherited`＝（`cost_is_inherited === true` 或自己成本不可用）且商品成本可用的款數。> 0 → `variant_cost_unconfirmed`，label `款式價格有缺（淘寶隱藏各款價格，{inherited} 款暫用商品成本）`。
   - 沒款式時：商品成本不可用 → `variant_cost_missing`，label `沒抓到成本`。
2. `same_price_with_range`：上一步兩個價格問題都沒有，且 `variants.length ≥ 2`、`hasHiddenVariantPriceEvidence(rawCapture.client_meta)`、`!isVariantPriceConfirmed(rawCapture)`、`allVariantCostsIdentical(variants, productCny)`。label `每款都同價（但頁面顯示價格有高低或被隱藏）`。
   - 沿用 `publishReadiness.ts` 的 `allVariantCostsIdentical`：**只加 `export`，不改邏輯**。
   - 為什麼不是「只要每款同價就紅」：潮玩盲盒本來就常常每款同價；只有頁面證據（hideOtherPrice、價格區間、外掛「個別未優惠價未完整取得」）說價格應該不同時才紅，跟發布前 PRICE-GUARD 同一個判斷。
3. `no_variants`：`variants.length === 0`，且頁面看得出有款式選項——任一成立：
   - `client_meta.sku_dimensions` 是數字 ≥ 1，且 `server.dropped_constant_axes`（陣列，沒有＝0）長度 < `sku_dimensions`（只有一個選項值、被 4a 拿掉的軸不算）；
   - `readHiddenVariantPriceEvidence(client_meta).priceRange` 為真；
   - `server.excluded_variants` 是非空陣列。
   label `0 個款式（頁面有款式選項）`。
4. `no_detail_images`：`detailImageCount === 0`。label `0 張詳情圖`。
- `incomplete`＝`issues.length > 0`。issues 順序＝上面的順序。
